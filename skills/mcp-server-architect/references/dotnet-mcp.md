# .NET MCP profile

## Project shape

Use application and domain projects that do not depend on MCP hosting packages. The host project references the official core, hosting, and ASP.NET Core integration packages needed by the selected transport. Register typed services in DI and expose thin tool classes or methods.

```csharp
builder.Services
    .AddMcpServer()
    .WithHttpTransport()
    .WithTools<InventoryTools>();
```

Choose stdio or HTTP explicitly. Stateless HTTP is the default when no cross-request session state is required.

## Dependency injection and request scope

Tool dependencies are constructor- or parameter-injected from DI. Request-specific data lives in the supported request context and scoped services. Do not use reflection to inspect private SDK registries. Do not use a singleton to hold caller identity or mutable request state.

## Cancellation and deadlines

Accept `CancellationToken` on every tool method that performs I/O and pass it to EF Core, `HttpClient`, streams, subprocesses, and delays. Avoid `.Result`, `.Wait()`, and sync-over-async. In HTTP hosting, distinguish transport abort from application deadline when the API allows it; both must stop downstream work.

## Error mapping

Use middleware, message filters, or a central adapter to map domain exceptions to stable MCP error categories. Catch locally only when the tool can add context or recover. Preserve `OperationCanceledException` semantics. Validation, authentication, authorization, conflict, timeout, unavailable dependency, and internal failure remain distinguishable.

## Correlation and telemetry

Use `ActivitySource` and OpenTelemetry for traces. Use `ILogger.BeginScope` for correlation and principal identifiers that are safe to log. `AsyncLocal` is reserved for infrastructure that cannot receive explicit context and must be cleared correctly.

## Validation

Use typed records and `System.Text.Json` schemas generated by the SDK. Add options validation and application validators for cross-field or resource rules. Validation occurs before I/O. Avoid accepting unbounded dictionaries when a stable record is possible.

## Concurrency and state

Use immutable snapshots, concurrent collections, or `SemaphoreSlim` according to ownership and contention. Do not place a process-wide lock around unrelated tools. For optimistic writes, expose and verify ETags, versions, or row tokens and require re-read before a conflict retry.

## Test host

Construct the real generic or ASP.NET Core host with test configuration. Replace application interfaces through DI, use `MockHttpMessageHandler` or a test server for HTTP, and use Testcontainers when protocol behavior of an external dependency matters. Invoke tools using the public MCP client, not reflection against tool classes alone.

## Deployment

Expose separate startup, readiness, and liveness checks when hosted with ASP.NET Core. Shutdown uses host lifetime, stops new work, and honors a bounded drain period. Container tests run as a non-root user when production does.

## Verification

Run analyzer-enabled build, unit and policy tests, real-host registration and invocation tests, cancellation propagation, structured error mapping, stdio output isolation when applicable, and a smoke test against the packaged artifact.
