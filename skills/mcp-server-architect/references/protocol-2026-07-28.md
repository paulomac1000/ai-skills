# MCP 2026-07-28 implementation profile

## Revision declaration

Every generated or assessed server MUST declare protocol support per SDK profile. A package version, language, or transport name does not prove a protocol revision. The declaration records:

- SDK package and exact version;
- supported protocol revisions;
- modern, legacy, or dual-era behavior;
- advertised transports;
- test commands and evidence for each claimed revision;
- unsupported or deprecated capabilities that remain only for compatibility.

The Python `mcp` 2.x profile supports the modern `2026-07-28` revision and legacy revisions from one server entrypoint. A different framework or package named FastMCP MUST use its own profile and evidence.

## Modern request contract

For `2026-07-28`, the server MUST implement a stateless protocol core:

- no `initialize` or `notifications/initialized` exchange on the modern path;
- no protocol session identity or `Mcp-Session-Id` on the modern Streamable HTTP path;
- optional `server/discover` for capability discovery;
- protocol version, client information, and client capabilities carried in request `_meta`;
- `Mcp-Method` and, where applicable, `Mcp-Name` headers on Streamable HTTP, validated against the JSON-RPC body;
- deterministic list ordering and cache hints where the SDK exposes them;
- `resultType: input_required` and `inputResponses` for multi-round-trip requests;
- Tasks treated as an extension rather than an assumed core capability.

Request-scoped application state MAY exist, but it MUST be explicit and MUST NOT depend on hidden transport affinity.

## Deprecated and removed behavior

New implementations SHOULD NOT introduce roots, sampling, or protocol logging. They MAY retain these capabilities on a declared legacy compatibility path while the selected SDK supports them. The evidence MUST distinguish “supported for compatibility” from “recommended for new design.”

The modern profile MUST NOT rely on removed methods such as `ping`, `logging/setLevel`, or legacy session/resumability behavior. Legacy HTTP+SSE remains forbidden for new ai-skills server designs even when an SDK can host a temporary named compatibility adapter.

## Dual-era acceptance

A dual-era profile MUST prove both paths independently:

1. A modern client performs `server/discover` or sends a direct self-describing request at `2026-07-28`.
2. The modern Streamable HTTP request contains the required routing headers and per-request `_meta`.
3. A legacy client negotiates through `initialize` at the specifically claimed earlier revision.
4. Both clients obtain the same application-owned capability identities and compatible schemas unless a documented revision difference applies.
5. A legacy-only feature does not leak a session requirement into the modern path.
6. Unsupported revisions and header/body mismatches fail deterministically.

Passing only the SDK unit tests or importing an SDK version is not protocol evidence.

## Minimum official-client matrix

For each advertised transport and revision, execute:

- discovery or initialization appropriate to the era;
- capability listing;
- one representative safe call;
- one validation or authorization failure path;
- response-bound and provenance checks;
- graceful shutdown and cancellation behavior;
- exact installed package or exact container identity check.

The assessment records `protocol_revisions` separately from runtime versions and operating-system combinations. A revision is `tested` only when the command and result are bound to the exact assessed source or artifact identity.
