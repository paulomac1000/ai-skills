# MCP 2026-07-28 implementation profile

## Revision declaration

Every generated or assessed server MUST declare protocol support per SDK profile. A package version, language, transport name, upstream release note, or design default does not prove a repository-tested protocol revision. The declaration records the SDK package and exact version, advertised revisions and transports, compatibility behavior, and the exact commands and evidence for every repository-level claim.

`2026-07-28` is the standard's default protocol target for new design work. It is **not** an automatic compatibility claim for every SDK profile. The profile manifest is authoritative for repository evidence. At this release, `python-official-mcp` records upstream-supported revisions but has no `repository_tested_revisions`, and `current_revision_support` remains `not-claimed`. FastMCP, .NET, and other profiles require their own independently produced evidence.

## Dual-era acceptance

Each claimed protocol revision MUST be exercised independently through the exact selected SDK and produced artifact. Support for a current revision does not prove support for an earlier revision, and upstream package support for either revision does not count as repository-tested evidence.

Before adding `2026-07-28` to a profile's `repository_tested_revisions`, verify the exact pinned SDK and exact produced artifact through an official client. Evidence must cover:

- initialize or negotiation behavior appropriate to the claimed revision;
- capability discovery and representative safe behavior;
- the profile's write and confirmation boundary where applicable;
- expected validation or authorization failure behavior;
- response bounds, provenance, shutdown, and cancellation behavior relevant to the profile;
- exact installed package or exact container identity rather than a source-tree import;
- any earlier-revision negotiation path that the profile also claims.

A profile may list a revision as upstream-supported without claiming that this repository has tested it. Do not infer compatibility across languages, frameworks, SDK package versions, generated baselines, or transport implementations.

## Migration rule

Existing projects are assessed against the SDK package and revision behavior they actually use. Do not force a project to advertise `2026-07-28` merely because this standard uses it as the design default. If the selected SDK cannot prove the required revision behavior, retain the project's compatible revision or defer the upgrade until an executable compatibility lane exists.

Protocol-era details such as stateless request shape, session behavior, discovery, headers, tasks, and legacy compatibility MUST come from the selected SDK/profile evidence. They are not universalized here ahead of repository-tested evidence.

## Verification

Keep the manifest and this record aligned. A repository-level support claim is valid only after exact-artifact official-client evidence is green and the manifest is updated deliberately. Until then, an empty `repository_tested_revisions` and `current_revision_support: not-claimed` are intentional fail-closed states, not missing documentation.
